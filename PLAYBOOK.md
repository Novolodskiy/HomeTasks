# Project Bootstrap Playbook

**Цель документа:** методология запуска нового мобильного / веб-проекта с использованием AI-агентов. Проверена на проекте HomeTasks.

**Когда применять:** при старте любого нового продуктового проекта, особенно с одним разработчиком + AI-агентами.

**Кто использует:** системный аналитик (Claude) и Product Owner. Аналитик ведёт по этапам, PO принимает решения.

---

## Общая структура процесса

```
Этап 0  →  Валидация идеи и позиционирование
Этап 1  →  Продуктовое определение (PRD)
Этап 2  →  Архитектура и технологический стек
Этап 3  →  Процессы разработки
Этап 4  →  Дизайн UI
Этап 5  →  Инфраструктура и аккаунты
Этап 6  →  Декомпозиция backlog
Этап 7  →  Разработка
Этап 8  →  Бета-тестирование
Этап 9  →  Прод-релиз
```

Каждый этап имеет свои deliverables, вопросы и артефакты. Этапы 0-5 идут последовательно, 6-9 итеративно.

---

## Этап 0 — Валидация идеи и позиционирование

**Цель:** понять что строим, для кого и зачем. Без этого все последующие решения плавают.

### Ключевые вопросы Product Owner-у

1. Какую проблему решает продукт?
2. Кто целевая аудитория? (возраст, профессия, контекст использования)
3. Какие альтернативы уже существуют? Чем мы лучше?
4. Какая бизнес-цель — стартап / лайфстайл-проект / для себя?
5. Какая модель монетизации? (подписка / реклама / freemium)
6. Какой целевой объём аудитории за первый год?
7. Где географически целевой рынок? (локально / регионально / глобально)
8. На каких платформах? (iOS / Android / web / desktop)

### Что обсудить отдельно

- **Платежи в регионе.** Если целевая аудитория в РФ или странах с ограниченным доступом к Apple/Google — выяснить рано, как будем брать деньги. Это влияет на стратегию запуска.
- **Конкурентный анализ.** Не делать «ещё один X» без чёткого отличия.
- **Ширина vs глубина.** Принять решение: делаем универсальный продукт или резкий фокус на одну фичу.

### Deliverables

- Краткое позиционирование (одно предложение)
- Целевые метрики на первый год (DAU, MRR, retention)
- Стратегия запуска (бета → коммерческий релиз; локальный → глобальный)

### Common pitfalls

- ❌ Не торопиться к коду, пока не ясен продукт
- ❌ Не предлагать «универсальное решение для всех» — оно нужно никому
- ❌ Не игнорировать региональные ограничения (платежи, законы, инфраструктура)
- ❌ Не проектировать сразу для миллиона пользователей — сначала валидируем на сотнях

## Этап 1 — Продуктовое определение (PRD)

**Цель:** зафиксировать **что именно** строим в виде формального документа.

**Артефакт:** `PRD.md` — Product Requirements Document.

### Структура PRD

1. Обзор продукта (vision, проблема, решение, позиционирование)
2. Целевая аудитория (основной сегмент, психографика)
3. Цели и метрики успеха
4. Стратегия запуска (этапы)
5. Скоуп MVP — **In Scope** и **Out of Scope** (последнее не менее важно)
6. User stories
7. Функциональные требования (бизнес-правила, нефункциональные требования)
8. UX-принципы
9. Описание экранов (детально — итеративно с PO)
10. Технический стек (кратко)
11. Монетизация
12. Риски и открытые вопросы

### Подэтап 1.1 — Скоуп MVP

Список фич делается через два списка:
- **In Scope** — что входит в первую версию
- **Out of Scope** — что **явно** не делаем (это критично, иначе агенты будут «улучшать» по своему усмотрению)

### Подэтап 1.2 — Описание экранов

**Делать итеративно, по одному экрану за раз.**

Для каждого экрана: показываем PO, согласуем, фиксируем в PRD, переходим к следующему. Не пытаться описать сразу все 9 экранов — PO даст обратную связь только после того, как реально вдумается в один.

Шаблон описания экрана:
- Назначение
- Когда открывается
- UI-элементы (сверху вниз)
- Поведение
- Чего нет (явные исключения)
- Edge-cases

### Common pitfalls

- ❌ Не предлагать сразу все экраны списком — PO утонет в деталях
- ❌ Не забывать о «чего нет» — это важная часть скоупа
- ❌ Не игнорировать обратную связь PO о терминах (например, «не staging, а стейдж») — фиксировать сразу
- ❌ Не предлагать фичи, которые PO явно отверг ранее

## Этап 2 — Архитектура и технологический стек

**Цель:** зафиксировать **как именно** устроена система.

**Артефакт:** `ARCHITECTURE.md`.

### Структура

1. Терминология окружений (фиксируется в начале)
2. Общая картина (диаграмма)
3. Что на клиенте
4. Что на сервере
5. Внешние сервисы
6. Сценарии работы (5-10 ключевых пользовательских флоу пошагово)
7. Масштаб и нагрузка (прогнозы на этапы запуска)
8. Что где хранится (таблица: данные → место хранения)
9. Безопасность
10. Стек технологий (итоговая картина)

### Ключевые архитектурные решения

Принять и зафиксировать:

- **Управляемое облако vs свой backend.** Для MVP с одним разработчиком — управляемое (Supabase, Firebase, Convex). Своё — только если есть веские причины.
- **Монорепо vs мульти-репо.** Для одного разработчика — монорепо. Для команды 5+ — обсуждать.
- **iOS+Android: одна кодбаза или две?** Cross-platform (Expo / Flutter) для одного разработчика. Native — только для специфических требований.
- **Серверные секреты.** API-ключи к платным сервисам (AI, payments) — **только** на серверной стороне (Edge Functions / Backend), не в коде клиента.
- **Окружения.** Минимум два: прод и стейдж. Локальная разработка через Docker.

### Прогноз нагрузки

Делать на три точки:
1. Закрытая бета (50-100 юзеров)
2. Открытая бета (500-2000 юзеров)
3. Прод-релиз через 1 год (10-50 тыс юзеров)

Для каждой — прикинуть стоимость инфраструктуры.

### Common pitfalls

- ❌ Не предлагать микросервисы для одного разработчика
- ❌ Не выбирать стек, который не знает разработчик, без веской причины
- ❌ Не зашивать AI-ключи в клиент (популярная ошибка с реальными финансовыми потерями)
- ❌ Не игнорировать оффлайн для мобильного приложения, если юзеры будут пользоваться в местах без сети

## Этап 3 — Процессы разработки

**Цель:** определить **как мы работаем** — статусы задач, ветки, ревью, тестирование.

**Артефакт:** `PROCESS.md`.

### Что определить

1. **Команда и роли** (Product Owner, аналитик, разработчики, тестировщик)
2. **Окружения** — что в проде, что в стейдже, как переключаемся
3. **Branching strategy** — feature → epic → master → prod
4. **Workflow задач** — статусы (Backlog → Ready → In Progress → Review → Testing → Done)
5. **Шаблон ТЗ внутри задачи** (что должно быть в каждом тикете)
6. **Как агент берёт задачу** (алгоритм выбора, защита от конфликтов)
7. **PR workflow** (template, ревью, мерж)
8. **Тестирование** (на задачу, на эпик, прод-релиз)
9. **Quality system** — слои защиты качества
10. **Automation rules** в системе тикетов (email-уведомления)

### Multi-layer quality system

Каждый слой ловит свой класс ошибок:

```
1. CLAUDE.md (системный промпт для агента)
2. Шаблон задачи (полное ТЗ с тестами)
3. TypeScript strict + ESLint + Prettier
4. Pre-commit hooks (Husky)
5. CI checks в GitHub Actions
6. Code Review (аналитик)
7. Ручное тестирование (PO)
```

Без всех слоёв — больше багов проникает в прод.

### Common pitfalls

- ❌ Не разделять жёстко «фронт-агента» и «бэк-агента» — лишний overhead на координацию
- ❌ Не ставить много параллельных агентов сразу — тестировщик будет узким местом
- ❌ Не игнорировать «куда агент пишет, когда нет задач» — нужен Communication Hub

## Этап 4 — Дизайн UI

**Цель:** получить визуальные макеты всех экранов.

**Артефакт:** `DESIGN_REQUIREMENTS.md` — ТЗ для AI-инструмента дизайна или человека-дизайнера.

### Структура DESIGN_REQUIREMENTS

1. Контекст продукта
2. Принципы дизайна (обязательные правила)
3. Визуальный стиль (цвета, типографика, иконки, скругления)
4. Платформенные конвенции (iOS HIG, Material Design)
5. Описание всех экранов (детально, копия из PRD)
6. Сквозные компоненты
7. Анимации (минимум)
8. Что НЕ должно быть
9. Состояния (loading, error, offline, empty)
10. Чек-лист для финального макета
11. Что отдать обратно (deliverables)

### Common pitfalls

- ❌ Не давать дизайнеру PRD как есть — там много текста, не релевантного для дизайна
- ❌ Не забывать про тёмную тему и состояния
- ❌ Не игнорировать платформенные конвенции (нативные паттерны iOS/Android)

## Этап 5 — Инфраструктура и аккаунты

**Цель:** настроить все внешние сервисы и аккаунты, нужные для разработки и релиза.

**Артефакт:** `SETUP_CHECKLIST.md` — пошаговый чек-лист.

### Что настроить (типовой набор для мобильного проекта)

1. **Доступность имени** — домены, App Store, товарный знак, соцсети
2. **Зарубежная карта** (если нужна для оплаты сервисов)
3. **Apple Developer аккаунт** ($99/год) — **запускать рано**, проверка до 2 недель
4. **Google Play Developer** ($25 разово) — за 1-2 недели до билда
5. **Таск-трекер** (Jira / Linear / GitHub Projects) + MCP-сервер
6. **GitHub** репозиторий с branch protection
7. **Облачный backend** (Supabase) — два проекта: stage и prod
8. **AI-сервисы** (OpenAI, Anthropic) — с лимитом расходов
9. **Build-сервис** (EAS Build для Expo)
10. **Связь Apple/Google со сборками** — API ключи, service accounts

### Какой таск-трекер выбрать

| Инструмент | Когда подходит |
|---|---|
| **Jira** | Стандарт индустрии, есть в большинстве компаний, MCP есть |
| **Linear** | Современнее, быстрее, для команд до 250 issues бесплатно |
| **GitHub Projects** | Простейшее, рядом с кодом, бесплатно навсегда |

Для AI-разработки все три имеют MCP-серверы. Главное — выбрать **тот, который привычнее PO**.

### Common pitfalls

- ❌ Не откладывать Apple Developer до момента когда билд готов — проверка занимает до 2 недель
- ❌ Не запускать оплачиваемые сервисы без установки лимитов (можно случайно потратить тысячи долларов)
- ❌ Не зашивать секреты в Git
- ❌ Не пропускать настройку **branch protection** в GitHub — без неё агент случайно сломает master

## Этап 6 — Декомпозиция backlog

**Цель:** разбить продукт на эпики и задачи, готовые к выполнению агентом.

**Артефакты:**
- Тикеты в Jira / Linear / GitHub Issues
- `docs/epics/<epic-name>.md` — системная аналитика для каждого эпика

### Подэтап 6.1 — Эпики

Декомпозировать продукт на 6-10 крупных функциональных блоков. Типовой набор:

1. Auth и регистрация
2. Основные сущности и CRUD
3. Главный экран и навигация
4. Ключевая фишка продукта (для каждого продукта своя)
5. Социальные функции / шаринг
6. Уведомления
7. Оффлайн / производительность
8. Подготовка к релизу (полировка, бета-тестирование)

### Подэтап 6.2 — Системная аналитика на эпик

Для каждого эпика — отдельный документ в `docs/epics/`. Структура:

1. Цель эпика
2. Скоуп (список задач)
3. Структура данных в БД (таблицы, поля, индексы)
4. RLS-политики (кто что видит)
5. API-контракты (как frontend дёргает backend)
6. Edge Functions (если есть)
7. Realtime-каналы
8. TypeScript типы
9. Push-уведомления
10. Edge cases и open questions
11. Зависимости от других эпиков
12. Sequence diagrams для сложных потоков

### Подэтап 6.3 — Задачи

Каждая задача:
- 0.5-2 дня работы
- **Vertical slice** — включает и фронт, и бэк, и тесты
- Имеет полное ТЗ
- Имеет инструкцию «как тестировать»
- Имеет Definition of Done

Шаблон описан в `PROCESS.md`, раздел 4.3.

### Подэтап 6.4 — Communication Hub

В таск-трекере создать **специальный тикет** (например, HT-1: «Agent Communication Hub») для общения между агентами и аналитиком. Туда агент пишет когда нет задач или нужно уточнение.

### Common pitfalls

- ❌ Не делать слишком крупные задачи (>2 дней) — агент потеряет контекст
- ❌ Не делать слишком мелкие задачи (<2 часов) — overhead на координацию
- ❌ Не пропускать системную аналитику эпика — агенты будут «угадывать» решения
- ❌ Не забывать про зависимости (Blocked by) — агент может взять заблокированную задачу

## Этап 7 — Разработка

**Цель:** агенты делают задачи из backlog, аналитик ревьюит, PO тестирует.

### Главный артефакт — CLAUDE.md

В корне репозитория. Системный промпт для AI-агентов разработки.

Содержит:
1. Контекст проекта
2. Технологический стек
3. Архитектурные принципы
4. Стандарты кода (TypeScript strict, имена, структура файлов)
5. Безопасность (ключи, RLS, Edge Functions)
6. Работа с конкретными технологиями (например, Supabase)
7. Стиль коммитов и PR
8. Алгоритм выбора задачи
9. Что делать при сомнениях
10. Что НЕ делать
11. Глоссарий (имена сущностей в коде)

### Цикл работы

```
Аналитик создаёт задачу → переводит в Ready
   ↓
Агент берёт задачу (по алгоритму из CLAUDE.md)
   ↓
Агент работает, создаёт PR, переводит в In Review
   ↓
Аналитик ревьюит PR
   ↓
Если ОК → мерж в эпическую ветку → Testing
Если правки → request changes → агент исправляет
   ↓
PO тестирует на стейдже
   ↓
Если ОК → Done
Если баг → создаём sub-task → Reopened
```

### Параллельная работа агентов

Начинать с **одного агента**. Добавлять второго когда:
1. Установился ритм (3-5 задач в день закрывается)
2. PO успевает тестировать без узкого места
3. API-контракты зафиксированы (типы из БД сгенерированы)
4. Найдены **независимые задачи** для распараллеливания

### Common pitfalls

- ❌ Не запускать сразу 4 агентов — PO станет узким местом
- ❌ Не пропускать code review «потому что некогда» — агент быстро накопит технический долг
- ❌ Не давать агенту задачу без полного ТЗ — он будет «угадывать»

## Этап 8 — Бета-тестирование

**Цель:** проверить продукт на реальных пользователях и собрать обратную связь.

### Подготовка

- Билды через TestFlight (iOS) и Internal Testing (Android)
- Найти 20-50 реальных бета-тестеров (не разработчиков)
- Подготовить feedback-форму или канал коммуникации (Telegram / Discord / email)

### Что валидировать

- Работают ли ключевые сценарии end-to-end
- Понятен ли UX без объяснений
- Используют ли юзеры главную фичу продукта
- Какие баги встречаются
- Какой retention через 7 / 14 / 30 дней

### Метрики

- Время от установки до первого ключевого действия
- Доля семей/команд, где зарегистрировано 2+ человек (для совместных продуктов)
- Частота открытия приложения
- Длина сессии

### Что делать с обратной связью

- Создавать **новые тикеты** в backlog с пометкой `feedback`
- Приоритизировать только **повторяющиеся** жалобы (один раз — не паттерн)
- Не реализовывать всё подряд — бета-юзеры часто хотят разное

---

## Этап 9 — Прод-релиз

**Цель:** опубликовать в App Store / Google Play.

### Подготовка к релизу

- [ ] Все эпики MVP в Done
- [ ] End-to-end сценарии прошли регресс
- [ ] Crash-rate <0.5%
- [ ] App Store / Google Play screenshots готовы
- [ ] Описание приложения на всех целевых языках
- [ ] Privacy Policy и Terms of Service на сайте
- [ ] App Privacy disclosures (Apple) заполнены
- [ ] Иконки приложения во всех размерах
- [ ] Categories выбраны (Productivity / Lifestyle и т.п.)
- [ ] Pricing и In-App Purchase настроены (если paid)
- [ ] Sentry / аналитика подключена

### Подача

```bash
# Применяем последние миграции к prod
supabase db push --linked --project-ref <prod-id>

# Деплой Edge Functions
supabase functions deploy --project-ref <prod-id>

# Сборка production билда
eas build --profile production --platform all

# Подача в сторы
eas submit --platform all
```

### После одобрения

- Запустить **поэтапный rollout** (10% → 25% → 50% → 100%) — на случай критичных багов
- Мониторить crash-rate, ошибки, нагрузку
- Готовить hot-fix план

### Маркетинг (отдельная тема)

- Product Hunt launch
- Контент в соцсетях
- Reddit / Hacker News
- ASO (App Store Optimization)
- Платный трафик через 1-2 месяца после релиза, когда продукт «зацепился» органически

## Уроки и принципы

Сводка того, что работает в этой методологии:

### 1. Документ как источник правды

Всё ключевое в Markdown в репозитории. Никаких устных договорённостей, чатов, разрозненных Notion-страниц. **Если решения нет в `docs/` — оно не принято.**

### 2. Итеративная декомпозиция

Не пытаться описать сразу всё. Согласовывать поэтапно: одна область → согласование → следующая.

### 3. Слои защиты качества

Не полагаться на один механизм. CLAUDE.md + автоматические проверки + code review + ручное тестирование вместе работают.

### 4. Раздельные пользователи в Jira

Разные аккаунты для аналитика и каждого агента — критично для отслеживания и отчётности.

### 5. Communication Hub

Специальный тикет, куда агенты пишут когда нет задач или нужно уточнение. Без него работа агентов невидима.

### 6. Один агент → потом два

Не запускать сразу несколько агентов. Узкое место — тестировщик.

### 7. Внешние сервисы — рано

Apple Developer запускать **до** начала разработки, не когда билд готов.

### 8. AI-ключи — только на сервере

Никогда не зашивать в клиент. Стандартная ошибка с реальными финансовыми потерями.

### 9. Spelling out the obvious

В CLAUDE.md и инструкциях агентам прописывать **очевидные** для человека правила. AI-агенты их не «понимают по контексту».

### 10. Memory + README в проекте

Системный аналитик (Claude) при новой сессии читает MEMORY.md → memory-запись → README.md проекта. Если эта цепочка работает — контекст полностью восстанавливается.

## 11. Сохранение контекста между сессиями

**Проблема:** при обновлении чата AI-агент теряет:
1. **Технический контекст** — какие решения приняты, какая архитектура
2. **Качественный контекст** — стиль работы пользователя, отвергнутые альтернативы, тон

Без специальных мер каждая новая сессия начинается «с нуля» — даже если документы есть, теряется тонкое понимание как работать с конкретным человеком.

### 11.1 Четыре уровня сохранения

| Уровень | Что хранит | Где |
|---|---|---|
| **1. Документы проекта** | Финальные решения, скоуп, архитектура, процесс | `*.md` в папке проекта (Git) |
| **2. Memory-записи** | Поведенческие паттерны, указатели на ресурсы | `~/.claude/projects/<project>/memory/` |
| **3. JSONL-логи** | Полная история всех сессий | `~/.claude/projects/<project>/*.jsonl` (автоматически) |
| **4. Triggered search** | Доступ к истории по триггерным фразам | Memory-запись типа `feedback` |

Без всех четырёх уровней либо теряется информация, либо способ её достать.

### 11.2 Документы проекта

Обязательные:

| Файл | Зачем |
|---|---|
| `README.md` | Точка входа, список всех документов, текущее состояние |
| `PRD.md` | Продуктовые требования, описания экранов |
| `ARCHITECTURE.md` | Стек, окружения, архитектурные решения |
| `PROCESS.md` | Workflow задач, ветки, ревью, тестирование |
| `CLAUDE.md` | Системный промпт для AI-агентов разработки |
| `DECISIONS_LOG.md` | Все ключевые решения с альтернативами и обоснованиями |
| `USER_CONTEXT.md` | Стиль работы пользователя, предпочтения, красные линии |
| `PLAYBOOK.md` | Этот файл (методология, копировать в новые проекты) |

Опциональные:

| Файл | Когда |
|---|---|
| `DESIGN_REQUIREMENTS.md` | Если ведётся UI-дизайн |
| `SETUP_CHECKLIST.md` | Если нужно настроить много инструментов |
| `chats/` | Markdown-summary важных сессий (необязательно) |
| `docs/epics/` | Системная аналитика по эпикам |
| `docs/adr/` | Architecture Decision Records |

### 11.3 Memory-записи

| Файл | Тип | Назначение |
|---|---|---|
| `MEMORY.md` | индекс | Список всех memory-записей (загружается автоматически) |
| `memory/project_*.md` | project | Состояние конкретного проекта |
| `memory/methodology_*.md` | reference | Указатели на методологии |
| `memory/feedback_*.md` | feedback | Поведенческие правила («триггер X → действие Y») |
| `memory/user_*.md` | user | Профиль пользователя |

**Принцип:** memory — это краткая шпаргалка с указателями. Документы — полное содержание. Не дублировать.

### 11.4 JSONL-логи

Claude Code **автоматически** сохраняет всю историю каждой сессии в:

```
~/.claude/projects/<project-folder-name>/*.jsonl
```

Каждый файл = одна сессия. Каждая строка = одно сообщение. Формат — JSON Lines.

**Что в логах есть:** все ваши вопросы, все мои ответы, все вызовы инструментов и результаты.
**Чего нет:** невербальный тон, эмоциональная калибровка.

### 11.5 Триггерные фразы для поиска в логах

Стандартный набор:

- «Найди в логах ...»
- «Поищи в истории ...»
- «Мы это обсуждали ...»
- «Помнишь как мы говорили про ...»
- «Вспомни как мы решили ...»
- «Что мы решили по поводу ...»

**Алгоритм при срабатывании:**

```
1. Извлечь ключевые слова из вопроса
2. grep по DECISIONS_LOG.md (быстрый поиск решений)
3. Если есть chats/*.md — grep по нему
4. Если не нашёл — grep -l по *.jsonl
5. Read нужных строк JSONL для контекста
6. Восстановить смысл и ответить кратко
7. Если не нашёл — честно сказать «не нашёл по такому ключу»
```

Зафиксировать в:
- `USER_CONTEXT.md` — для будущих сессий при чтении контекста
- Memory-запись типа `feedback` (например, `feedback_search_in_logs.md`) — для автоматического срабатывания

### 11.6 Стартовая фраза для новой сессии

В зависимости от потребности:

**Минимум:**
> Продолжаем `<project>`.

**Стандарт (рекомендую):**
> Продолжаем `<project>`. Ты системный аналитик. Прочитай README.md и memory, расскажи где остановились.

**С акцентом на стиль:**
> Продолжаем `<project>`. Ты системный аналитик. Прочитай USER_CONTEXT.md внимательно — это про мой стиль работы. Потом README.md.

### 11.7 Алгоритм восстановления контекста в новой сессии

```
1. Открыть Claude Code в папке проекта /Users/user/Desktop/<project>/
   — критично, иначе MEMORY.md не загрузится автоматически

2. Пользователь пишет стартовую фразу

3. AI-агент:
   a. MEMORY.md уже в context (автоматически)
   b. Читает memory-записи (project_*, feedback_*)
   c. Читает README.md проекта
   d. Читает USER_CONTEXT.md
   e. По необходимости — DECISIONS_LOG.md, PRD.md, ARCHITECTURE.md

4. AI-агент даёт краткий доклад:
   "Я системный аналитик проекта X. Прочитал документацию.
   Где мы остановились: [...]
   Открытые вопросы: [...]
   Следующий шаг: [...]"

5. Пользователь подтверждает или корректирует контекст

6. Продолжается работа
```

### 11.8 Что эта методология не сохраняет

Часть всё равно теряется при обновлении сессии:

❌ Невербальные сигналы из обсуждений
❌ Тон отдельных дискуссий
❌ Микро-калибровка стиля общения
❌ Эмоциональный контекст моментов

**Это компромисс системы**, не баг. Решения:
- Держать одну сессию открытой как можно дольше — пока context не переполнится
- Документировать решения сразу, не в конце
- Обновлять `USER_CONTEXT.md` после неприятных моментов

### 11.9 Чек-лист применения на новом проекте

При старте нового проекта добавить к шагам PLAYBOOK:

- [ ] Создать `README.md` сразу при старте
- [ ] Создать `DECISIONS_LOG.md` сразу — обновлять при каждом решении
- [ ] Создать `USER_CONTEXT.md` сразу — обновлять по мере работы
- [ ] Создать memory-запись `project_<name>.md` (тип `project`)
- [ ] Скопировать с предыдущего проекта memory-запись `feedback_search_in_logs.md`
- [ ] Обновить `MEMORY.md` индекс — добавить ссылку на новый проект
- [ ] При обновлении сессий — использовать стандартную стартовую фразу
