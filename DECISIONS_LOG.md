# HomeTasks — Лог решений

**Цель документа:** для каждого ключевого решения зафиксировать **что выбрали, какие были альтернативы, и почему отвергли остальные**. Это позволяет:
- В будущем понять «почему так» — не возвращаться к уже отвергнутому
- В новых проектах — переиспользовать обоснования
- При сомнениях — увидеть полную картину рассмотрения

**Правило:** добавлять запись здесь сразу после принятия решения. Старые записи не удалять — только дополнять/корректировать.

## Продукт

### 2026-05-05 · Имя приложения: HomeTasks

**Альтернативы:**
- Dual / Dual Tasks
- Hearth, Nest, Kin, Tide, Beam, Pace, Tally, Knot

**Выбрано:** HomeTasks

**Почему отвергнуто:**
- **Dual / Dual Tasks** — звучит как «для пары», не для семьи. Tasks слишком generic, домен и App Store-имя застолбить невозможно
- **Короткие brand-имена (Hearth, Nest, Kin)** — не выбраны пользователем, требуют брендового продвижения

**Открытое:** проверить доступность доменов и App Store-имени до подачи в Apple Developer.

---

### 2026-05-05 · Целевая аудитория: семьи 2-8 человек

**Альтернативы:** пары, индивидуальные пользователи, команды на работе

**Выбрано:** семьи (родители 28-50, 0-3 ребёнка)

**Почему отвергнуто:**
- **Пары** — слишком узкий рынок
- **Индивидуальные** — конкуренция с Todoist, Apple Reminders слишком жёсткая
- **Рабочие команды** — другая динамика, нужно много фич для коллабораций

---

### 2026-05-06 · Скоуп MVP: только основные фичи

**Что НЕ делаем в MVP:**
- Категории задач, теги
- Приоритеты (high/medium/low)
- Recurring задачи
- Календарный view
- Геолокационные напоминания
- Шаблоны задач
- Apple Sign-in / Google Sign-in (только email/password)
- AI-классификация по категориям
- RuStore

**Почему:** принцип «низкое трение + узкий фокус». Каждая фича — это сложность для пользователя и работа для разработчика.

## Стратегия запуска

### 2026-05-05 · Этапы релиза: русская бета бесплатно → глобальный paid

**Альтернативы:**
- Сразу глобальный английский релиз
- Только русский релиз (на русскоязычной аудитории)

**Выбрано:** русская бета бесплатно (50-100 семей) → потом английский paid релиз

**Почему отвергнуто:**
- **Сразу глобальный** — пользователь не имеет англоязычной аудитории для валидации продукта
- **Только русский** — Apple/Google платежи в РФ не работают, монетизация невозможна

**Архитектурно:** i18n заложен с первого дня, чтобы добавление английского было просто JSON-файлом.

## Архитектура

### 2026-05-06 · Backend: Supabase, не свой

**Альтернативы:**
- Свои микросервисы на Node/Go/Python + AWS/GCP
- Firebase
- Convex / другие BaaS

**Выбрано:** Supabase

**Почему отвергнуто:**
- **Свой backend** — 3-4 месяца разработки, нет команды DevOps. У нас цель «бета за 2-3 недели». Технически невозможно
- **Микросервисы** — для одного разработчика это архитектурная роскошь, которая убьёт проект (Uber/Netflix перешли на это только при тысячах разработчиков)
- **Firebase** — Google ecosystem, vendor lock-in серьёзнее
- **Convex** — менее зрелый, меньше материалов

**Преимущества Supabase:** под капотом стандартная PostgreSQL, можно мигрировать. RLS на уровне БД (безопасность). Realtime из коробки.

---

### 2026-05-06 · Стек frontend: Expo (React Native) + TypeScript

**Альтернативы:**
- Native iOS (Swift) + Native Android (Kotlin) — две отдельные команды/репозитория
- Flutter (Dart)
- React Native без Expo

**Выбрано:** Expo + React Native + TypeScript

**Почему отвергнуто:**
- **Native** — в 3-4 раза больше работы, не подходит для одного разработчика
- **Flutter** — хороший выбор, но React Native имеет большее AI-комьюнити (Claude/Cursor лучше пишут код)
- **React Native без Expo** — больше boilerplate, нужно настраивать сборку самому

**Преимущества Expo:** OTA-апдейты без переподачи в стор, EAS Build для кросс-платформенной сборки, упрощённая настройка.

---

### 2026-05-06 · Один монорепо, не несколько

**Альтернативы:**
- Отдельные репозитории: ios/, android/, backend/
- Frontend и backend в разных репозиториях

**Выбрано:** один монорепо `hometasks/` для всего

**Почему отвергнуто:**
- **iOS+Android отдельно** — Expo генерирует обе платформы из одной кодбазы, разделять физически бессмысленно
- **Frontend+Backend отдельно** — синхронизация изменений схемы БД с UI кодом усложняется. Для одного разработчика overhead

---

### 2026-05-06 · AI-сервисы только через Edge Functions

**Альтернативы:** прямой вызов OpenAI/Anthropic с мобильного клиента

**Выбрано:** все AI-вызовы (Whisper, Claude) через Supabase Edge Functions

**Почему отвергнуто:**
- API-ключи в коде клиента можно извлечь из бинарника. Реальные кейсы — счета на $50K за неделю
- Edge Function позволяет управлять промптами без выпуска новой версии приложения
- Можно мониторить и лимитировать использование

---

### 2026-05-06 · Окружения: прод и стейдж

**Альтернативы:**
- Только прод (без стейджа)
- Прод + стейдж + dev environments per branch

**Выбрано:** два окружения — прод и стейдж

**Почему отвергнуто:**
- **Только прод** — нельзя тестировать перед релизом, регресс будет ломать пользователей
- **Per-branch dev environments** — overhead. Для одного разработчика хватит общего стейджа

**Конкретно:** один общий Supabase staging проект для master + всех dev-веток. Все preview билды смотрят туда.

---

### 2026-05-06 · TestFlight: разные Bundle ID для разных билдов

**Альтернативы:**
- Один Bundle ID, разные версии в TestFlight
- Разные Bundle ID для master, dev-веток и прод

**Выбрано:** разные Bundle ID

**Почему:** на телефоне тестера это разные приложения с разными иконками — можно ставить все одновременно (HomeTasks Master, HomeTasks Voice, HomeTasks Comments). Ошибиться невозможно.

## Платежи

### 2026-05-06 · Apple IAP + Google Play Billing через RevenueCat

**Альтернативы:**
- Stripe внутри приложения (запрещено правилами Apple/Google)
- Веб-флоу через ЮKassa (для российских юзеров)
- RuStore + RuStore Pay
- Гибрид всех вариантов

**Выбрано:** только Apple IAP + Google Play Billing через RevenueCat

**Почему отвергнуто:**
- **Stripe внутри iOS app** — нарушение правил Apple, бан приложения
- **ЮKassa веб-флоу** — российские карты не работают с Stripe, Apple банит за упоминание внешней оплаты
- **RuStore** — отдельная разработка, маленькая аудитория, +1-2 недели работы. Решено добавить только если будет смысл

**Последствие:** русские юзеры не смогут платить через сторы (только через зарубежный Apple ID + зарубежная карта). Поэтому **русская бета бесплатна.**

## Процесс

### 2026-05-06 · Jira как таск-трекер (через MCP)

**Альтернативы:** Linear, GitHub Projects, Notion, YouTrack

**Выбрано:** Jira Free tier

**Почему отвергнуто:**
- **Linear** — современнее, но платный после 250 issues. Для роста нужно платить
- **GitHub Projects** — рассмотрено, но Jira даёт больше структурных возможностей (custom fields, automation rules)
- **Notion** — не специально для задач
- **YouTrack** — менее популярен в AI-tooling

**Преимущества Jira:** стандарт индустрии, бесплатный tier до 10 пользователей, MCP сервер существует (`mcp-atlassian`), привычно для PO.

---

### 2026-05-06 · Документация в репозитории, не в Confluence

**Альтернативы:** Confluence, Notion, GitBook

**Выбрано:** Markdown в `docs/` репозитория

**Почему отвергнуто:**
- **Confluence** — overkill для одного разработчика, медленный UI, дублирует то, что и так есть в репо
- **Notion** — хорош, но требует отдельной интеграции для агентов
- **GitBook** — для красивой публичной документации, не для рабочей

**Преимущества Markdown в репо:** бесплатно, версионируется с кодом, доступно агентам без дополнительной настройки, можно читать прямо в GitHub.

---

### 2026-05-06 · Один аналитик/архитектор, не разделять

**Альтернативы:** разделить на отдельных агентов — System Analyst и Architect

**Выбрано:** одна роль (System Analyst + Architect)

**Почему отвергнуто:**
- Эти роли пересекаются на 80% (декомпозиция эпика = и БД и задачи)
- Coordination overhead между двумя агентами съест выгоду
- Разные context windows у двух агентов = синхронизация через документы тормозит работу

**Используемые инструменты для управления контекстом:** узкие сессии для конкретных задач, документы как внешняя память, sub-agents для исследовательских задач.

---

### 2026-05-06 · 1 разработчик-агент на старте, не 3-4

**Альтернативы:** запустить 3-4 параллельных агентов для скорости

**Выбрано:** один агент-разработчик на старте, второй когда установится ритм

**Почему отвергнуто:**
- Узкое место — тестировщик (PO). Реалистично 2-3 задачи в день качественного тестирования
- 4 агента = очередь из задач на тестирование, агенты простаивают
- Code review тоже узкое место без отдельного ревьюера

**Когда добавлять второго:** когда установится ритм 3-5 задач/день и появятся независимые задачи для распараллеливания.

---

### 2026-05-06 · Communication Hub в Jira (тикет HT-1)

**Альтернативы:**
- Slack / Telegram канал
- Email
- Без отдельного механизма

**Выбрано:** специальный тикет HT-1 «Agent Communication Hub» в Jira со статусом всегда In Progress

**Почему:** агент пишет туда комментарий когда нет задач или нужно уточнение, Jira Automation шлёт email-уведомление. Не требует отдельной интеграции.

---

### 2026-05-06 · Раздельные пользователи в Jira

**Альтернативы:** один сервисный аккаунт «AI-Bot» для всех агентов

**Выбрано:** разные пользователи (Дмитрий, Claude Analyst, Agent-1)

**Почему:**
- В поле Assignee видно конкретного исполнителя
- История изменений показывает кто что менял
- Можно фильтровать по исполнителю
- Раздельные права доступа

---

### 2026-05-06 · Email/password в MVP, без Apple/Google Sign-in

**Альтернативы:** добавить Apple Sign-in (обязательно для App Store если есть Google) и Google Sign-in

**Выбрано:** только email/password в MVP

**Почему:** Apple Sign-in добавляет 2-3 дня работы. На бета-этапе достаточно email/password. Apple Sign-in добавим перед глобальным релизом (там он становится **обязательным**, если есть Google).

## Дизайн

### 2026-05-06 · Главный экран — список из 4 секций, не табы и не kanban

**Альтернативы:**
- Tab bar внизу с 4 табами (Today/Soon/Later/Archive)
- Kanban-доска с колонками
- Один общий список с фильтрами

**Выбрано:** скроллящийся список с 4 секциями (Сегодня / Скоро / Когда-то / Архив)

**Почему отвергнуто:**
- **Tab bar** — лишнее переключение, юзер не видит общую картину
- **Kanban** — для семьи это сложно. Семья из 4 человек × 50 задач = месиво
- **Один список с фильтрами** — фильтры скрывают информацию, юзер забывает что они применены

---

### 2026-05-06 · Голос — push-to-talk, не диалоговое окно

**Альтернативы:**
- Открыть диалоговое окно с кнопками Стоп/Готово
- Tap-to-record (тапнул, говоришь, тапнул чтобы остановить)
- Push-to-talk (зажал, говоришь, отпустил)

**Выбрано:** push-to-talk (как в WhatsApp/Telegram)

**Почему отвергнуто:**
- **Диалоговое окно** — лишний промежуточный экран, больше кликов
- **Tap-to-record** — можно случайно начать или забыть остановить

**Преимущество push-to-talk:** знакомый паттерн, физический контроль начала/конца записи, нет зависимости от auto-stop.

---

### 2026-05-06 · AI оформляет голос, не просто транскрибирует

**Альтернативы:**
- Просто транскрипция (Whisper → текст в title)
- Транскрипция + ручное редактирование пользователем

**Выбрано:** Whisper транскрибирует → Claude Haiku оформляет в структурированную задачу (title, description, deadline, assignee)

**Почему:** «эээ типа купить молоко короче на завтра» → «Купить молоко» (на завтра). Пользователь говорит как удобно — на выходе аккуратная задача.

---

### 2026-05-06 · Карточка задачи: 3 кнопки внизу — Выполняю/Выполнено/Отменить

**Альтернативы:**
- Только Выполнено/Отменить (без Выполняю)
- Чекбокс «выполнено» рядом с задачей в списке
- Кнопка удаления

**Выбрано:** 3 кнопки — Выполняю / Выполнено / Отменить

**Почему:**
- **Выполняю** переносит задачу в секцию Сегодня (для долгих задач)
- **Выполнено / Отменить** — два варианта закрытия (для статистики)
- Кнопки удаления нет — есть «Отменить»

---

### 2026-05-06 · Realtime комментарии (не pull-to-refresh)

**Альтернативы:** обновление при тапе или возврате в приложение

**Выбрано:** realtime через Supabase Realtime

**Почему:** эффект «мама пишет — папа сразу видит». Это создаёт ощущение совместного пространства. Технически бесплатно (Supabase Realtime включён в Free tier).

## Memory / Восстановление контекста

### 2026-05-06 · CLAUDE.md = общая база, ролевая специфика в .claude/agents/

**Альтернативы:**
- Один большой CLAUDE.md со всем (для всех ролей)
- CLAUDE.md только для разработчика, аналитик использует другие файлы (USER_CONTEXT, PROCESS)
- CLAUDE.md = общая база + ролевые файлы для каждой роли

**Выбрано:** CLAUDE.md = общая база + `.claude/agents/developer.md` и `.claude/agents/analyst.md` для специфики

**Почему отвергнуто:**
- **Один большой файл** — становится огромным, агент должен сам выбирать что читать, риск пропустить релевантное
- **CLAUDE.md только для разработчика** — аналитик не имеет своего ролевого файла, специфика размазана по другим документам

**Принципы разделения:**
- В CLAUDE.md остаётся ВСЁ что нужно знать **обоим**: для работы И для контроля при ревью (стандарты кода, безопасность, архитектура, миграции, realtime, глоссарий, продуктовые ограничения)
- В роль-файлах — только **операционная специфика** (как брать задачу, как ревьюить, communication)
- Аналитик при ревью PR дополнительно читает developer.md — чтобы знать как должен был работать разработчик

**Структура:**
```
CLAUDE.md                              ← читают все автоматически
.claude/agents/developer.md            ← разработчик-агент
.claude/agents/analyst.md              ← аналитик/ведущий
```

**Стратегия восстановления:** в новой сессии читать MEMORY.md → memory-записи → README.md → USER_CONTEXT.md. Если нужен исторический контекст — grep по `~/.claude/projects/-Users-user-Desktop-Tasks/*.jsonl`.
