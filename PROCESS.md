## 3. Branching strategy в Git

```
master                                        ← всегда стабильная, отражает стейдж
└── epic/auth                                  ← эпическая ветка
    ├── feature/HT-2-setup-project
    ├── feature/HT-3-auth-screens-skeleton
    ├── feature/HT-4-signup
    └── feature/HT-5-signin
```

**Правила:**
- Каждая dev-задача = отдельная feature-ветка от эпической ветки
- Имя ветки: `feature/HT-XX-краткое-описание` (HT-XX — номер тикета Jira)
- Feature-ветки мержатся в эпическую ветку через PR
- Эпическая ветка мержится в master, когда все задачи эпика готовы и протестированы
- Master деплоится автоматически на стейдж после merge
- Прод-релиз — отдельная ручная команда из master

## 4. Workflow задач в Jira

### 4.1 Статусы

| Статус | Что значит | Кто переводит |
|---|---|---|
| **Backlog** | Задача создана, но ТЗ не готово или есть открытые блокеры | Аналитик создаёт здесь |
| **Ready** | ТЗ полное, нет блокеров. Можно брать в работу | Аналитик переводит когда готово |
| **In Progress** | Агент взял в работу | Агент переводит сам |
| **In Review** | Агент создал PR, нужно ревью кода | Агент переводит после создания PR |
| **Testing** | PR смержен в эпическую ветку, ждёт ручного тестирования | Аналитик после ревью и мержа |
| **Done** | Задача протестирована и закрыта | Тестировщик после успешного теста |
| **Reopened** | Найден баг при тестировании, возвращена в работу | Тестировщик при обнаружении бага |

### 4.2 Поля задачи

Каждая задача содержит:

- **Summary** — короткое название
- **Epic Link** — связь с эпиком
- **Description** — структурированное ТЗ (см. шаблон ниже)
- **Priority** — Highest / High / Medium / Low
- **Assignee** — конкретный агент или пусто
- **Blocked by** / **Blocks** — зависимости с другими задачами
- **Labels** — `frontend`, `backend`, `setup`, `bug`, `tech-debt`
- **Story Points** или **Estimate** — примерная оценка (часы)

### 4.3 Шаблон ТЗ внутри задачи

```markdown
## Контекст
[Зачем задача нужна, к какому эпику относится, что предшествовало]

## Технические требования
[Конкретные файлы которые нужно создать/изменить, какие компоненты,
какие API использовать. Желательно с примерами кода и ссылками на
документ системной аналитики docs/epics/XX-name.md]

## Definition of Done
- [ ] Все TypeScript-проверки проходят (`pnpm typecheck`)
- [ ] Линтер не ругается (`pnpm lint`)
- [ ] Код отформатирован (`pnpm format`)
- [ ] PR создан и связан с тикетом
- [ ] Ручное тестирование пройдено (см. ниже)
- [ ] Описание изменений в PR заполнено

## Как тестировать
[Пошаговая инструкция: что открыть, что нажать, что увидеть.
Включая edge cases и негативные сценарии]

1. Запустить приложение на iOS / Android
2. ...
3. **Ожидаемо:** ...

Edge cases:
- ...
- ...

## Зависимости
- Блокируется задачей: HT-X
- Блокирует задачи: HT-Y, HT-Z

## Эстимейт
~1 день
```

### 4.4 Эпик: системная аналитика и приёмочные критерии

Каждый эпик имеет два связанных артефакта:

1. **Документ системной аналитики** в `docs/epics/XX-name.md` — пишет аналитик до начала разработки. Содержит схему БД, RLS-политики, API-контракты, Edge Functions, Sequence diagrams.

2. **Acceptance criteria в самом тикете эпика** — приёмочные тесты на эпик целиком. Прогоняются после мержа эпической ветки в master.

## 5. Как агент берёт задачу в работу

Жёсткие правила (записаны в [CLAUDE.md](CLAUDE.md)):

### 5.1 Алгоритм выбора задачи

```
1. Через Jira MCP запросить задачи проекта HT с фильтрами:
   • Status = "Ready"
   • Assignee = empty или me

2. Сортировать по Priority (Highest first), при равенстве — по дате создания.

3. Прочитать "Blocked by" — если есть открытые блокеры, пропустить.

4. Атомарно:
   • Поставить себя в Assignee
   • Перевести Status в "In Progress"

5. Если конфликт (другой агент опередил) — взять следующую.

6. Если задач нет в Ready — НЕ ВЫДУМЫВАТЬ работу.
   Написать комментарий в HT-1 (Communication Hub):
   "[Agent-X] Нет задач в Ready, останавливаюсь."
   Завершить работу.
```

### 5.2 Перед началом кодинга

```
1. Прочитать ВСЁ описание задачи целиком.
2. Прочитать связанный документ системной аналитики docs/epics/XX-name.md.
3. Прочитать CLAUDE.md (системный промпт).
4. Если что-то неясно в ТЗ — НЕ КОДИТЬ. Написать комментарий
   в задачу с уточнением, вернуть в Ready, остановиться.
5. Только когда всё ясно — начать работу.
```

### 5.3 Communication Hub (HT-1)

Специальная задача в Jira, которая всегда в статусе In Progress. Используется для коммуникации:

- Агенты пишут когда нет работы
- Агенты пишут о неоднозначных решениях
- Аналитик пишет общие инструкции

Формат комментария:
```
[Agent-1] [HT-12 → Done] В Ready задач нет. Останавливаюсь.
[Agent-2] [HT-15] Не понятно: какой формат хранения дедлайна — UTC или local?
[Analyst] Завтра приоритеты пересматриваются, держите Ready пустой.
```

## 6. Назначение задач агентам

### 6.1 Режим 1 — Аналитик назначает явно (по умолчанию)

1. Аналитик создаёт задачу
2. Видит свободного агента (нет In Progress)
3. Назначает Assignee = Agent-X
4. Переводит Status в Ready
5. Агент при чек-ине Jira видит свою задачу → берёт

### 6.2 Режим 2 — Очередь без assignee (для масштаба)

1. Аналитик создаёт задачу, Assignee пусто
2. Переводит в Ready
3. Любой свободный агент берёт первую по приоритету

На старте используем Режим 1 — больше контроля. Переход на Режим 2 — когда появится 2+ агентов и установится ритм.

## 7. Pull Request workflow

### 7.1 Создание PR

Когда агент закончил задачу:

1. Push feature-ветку в GitHub
2. Создать PR от feature-ветки в эпическую ветку
3. Заполнить PR template (см. ниже)
4. Связать PR с тикетом Jira (упомянуть HT-XX в описании)
5. Перевести задачу в статус **In Review**

### 7.2 PR Template

```markdown
## Связь с задачей
- Closes HT-XX

## Что сделано
- [Краткое описание изменений]

## Как тестировать
- [Шаги для ревьюера]

## Чек-лист
- [ ] Код проходит TypeScript checks
- [ ] Linter не ругается
- [ ] Описание/документация обновлены, если нужно
- [ ] Не зашиты секреты в код
- [ ] Не нарушены правила из CLAUDE.md
```

### 7.3 Code Review

Делает аналитик (Claude). Чек-лист ревью:

- Соответствие ТЗ из задачи
- Соответствие архитектурным правилам из CLAUDE.md
- Безопасность (нет утечек ключей, есть RLS)
- Стиль кода (typescript strict, нет any)
- Нет лишнего: задача не должна трогать файлы вне scope
- Edge cases учтены (по «Как тестировать» из задачи)

Если всё ок → approve → мерж в эпическую ветку → перевод задачи в Testing.

Если есть замечания → request changes → агент исправляет → повторное ревью.

## 8. Тестирование

### 8.1 Тестирование задачи (на стейдже)

После мержа в эпическую ветку:
- Автоматическая сборка нового preview build (через EAS Build) с теми же изменениями
- Билд загружается в TestFlight (iOS) и Internal Testing (Android)
- Тестировщик (Дмитрий) получает уведомление
- Открывает Jira, читает «Как тестировать»
- Прогоняет шаги на телефоне с preview build
- Если ОК → переводит задачу в **Done**
- Если баг → создаёт sub-task с описанием → возвращает родительскую задачу в **Reopened**

### 8.2 Тестирование эпика (после мержа в master)

Когда все задачи эпика в Done и эпическая ветка мержится в master:
- Автоматически собирается новый master-билд preview
- Тестировщик прогоняет **acceptance criteria эпика** (end-to-end сценарии)
- Если ок → эпик закрыт, готов к релизу в прод
- Если найдены баги — заводим тикеты и исправляем перед прод-релизом

### 8.3 Прод-релиз

Когда несколько эпиков накопилось и готовы — делаем прод-релиз:
1. Применяем миграции БД к production Supabase
2. Деплоим Edge Functions в production
3. Собираем production build приложения через `eas build --profile production`
4. Подаём в App Store / Google Play
5. После одобрения — раскатывание

## 9. Quality system — слои защиты

```
Слой 1: Системный промпт CLAUDE.md         → агент сам соблюдает правила
Слой 2: Шаблон задачи в Jira               → ТЗ полное и тестируемое
Слой 3: TypeScript strict + ESLint + Prettier → автоматические проверки
Слой 4: Pre-commit hooks (Husky)           → блок коммита если правила нарушены
Слой 5: CI checks в GitHub Actions         → блок мержа PR если что-то не так
Слой 6: Code Review (аналитик)             → логика и архитектура
Слой 7: Ручное тестирование (Дмитрий)      → поведение продукта
```

Каждый слой ловит свой класс ошибок. Без всех слоёв — больше багов проникает.

## 10. Jira Automation Rules

Настраиваются в Jira → Project Settings → Automation. Все бесплатно во Free tier.

### Правила, которые нужно создать:

| Триггер | Действие |
|---|---|
| Issue transition to Done | Email System Analyst |
| Issue transition to Testing | Email Product Owner (нужно протестировать) |
| Comment added to HT-1 | Email System Analyst |
| Issue created with mention `@analyst` | Email System Analyst |
| Issue in In Progress more than 24h без комментариев | Email System Analyst (агент завис?) |
| GitHub PR created (через webhook) | Auto-transition Issue → In Review |

## 11. Конкретные команды разработчика

### 11.1 Локальная разработка

```bash
# Запустить локальный Supabase
supabase start

# Запустить мобильное приложение
npx expo start

# Применить миграции локально
supabase db reset
```

### 11.2 Деплой миграций на стейдж

```bash
supabase db push --linked --project-ref <stage-id>
```

### 11.3 Сборка билда для TestFlight / Internal Testing

```bash
eas build --profile master --platform all
```

### 11.4 Деплой Edge Function на стейдж

```bash
supabase functions deploy process-voice --project-ref <stage-id>
```

### 11.5 Деплой на прод

```bash
supabase db push --linked --project-ref <prod-id>
supabase functions deploy --project-ref <prod-id>
eas build --profile production --platform all
eas submit --platform all
```

## 12. Что НЕ делать

❌ Не мержить в master без зелёного CI и одобрения ревьюера  
❌ Не работать на проде «по-быстрому» — все изменения через ветки  
❌ Не пушить секреты в Git (использовать `.env`, `supabase secrets`)  
❌ Не использовать `git push --force` в master  
❌ Не пропускать ручное тестирование на стейдже  
❌ Не задерживать перевод задач в нужный статус (это ломает видимость)
