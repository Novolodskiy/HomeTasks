## 1. Контекст проекта

**HomeTasks** — мобильное приложение для семейного управления бытовыми задачами. Главная фишка — голосовое создание задач: юзер говорит произвольную фразу, AI обрабатывает её и создаёт структурированную задачу.

**Этап:** разработка MVP для закрытой беты на русском (50-100 семей). Дальше — глобальный платный релиз на английском.

**Команда:**
- Один Product Owner (Дмитрий Новолодский)
- Один System Analyst (Claude — создаёт задачи и делает ревью)
- 1-2 разработчика-агента

## 2. Стек

**Frontend:**
- Expo (React Native) + TypeScript (strict mode)
- Expo Router (file-based routing)
- NativeWind (Tailwind for React Native)
- TanStack Query (server state)
- Expo SQLite + AsyncStorage (локальное хранилище)
- expo-speech-recognition или expo-av для голоса
- Expo Notifications (push)
- i18next + expo-localization

**Backend:**
- Supabase (Postgres + Auth + Storage + Realtime + Edge Functions)
- Deno + TypeScript для Edge Functions

**AI:**
- OpenAI Whisper API (транскрипция)
- Anthropic Claude Haiku 4.5 (парсинг текста в структуру задачи)
- Оба вызываются **только из Edge Functions**, не с клиента

**Инструменты:**
- GitHub (репозиторий)
- Jira (задачи) + MCP-сервер
- EAS Build (сборки)
- Supabase CLI (миграции, функции)

**НЕ предлагай смену стека без явного запроса от Product Owner.**

## 3. Архитектурные принципы

### Монорепо
Один репозиторий для всего: фронт, бэк, миграции, Edge Functions, документация.

### Структура папок
```
app/                            # Expo Router — экраны
src/components/                 # Общие UI компоненты
src/features/<feature>/         # Бизнес-логика по фичам
src/lib/                        # Утилиты (supabase client, i18n)
src/locales/                    # Переводы UI
src/types/database.ts           # Автогенерируется из Supabase, не править руками
supabase/migrations/            # SQL миграции
supabase/functions/<func>/      # Edge Functions
docs/                           # Документация (системная аналитика, ADR)
```

### Один компонент — одна ответственность
Не пиши «универсальные компоненты на все случаи жизни». Лучше два специализированных, чем один с десятью props.

### Не дублируй логику
Если функция используется в двух местах — выноси в `src/lib/` или в общий хук.

### Типы из БД генерируются автоматически
После любой миграции БД нужно обновить `src/types/database.ts`:
```bash
supabase gen types typescript --linked > src/types/database.ts
```
**Никогда** не править этот файл руками.

## 4. Стандарты кода

### TypeScript

- **strict mode обязательно**: `"strict": true` в `tsconfig.json`
- **Никаких `any`** — если нужен временный обход, используй `unknown` и cast явно
- **Никаких `// @ts-ignore`** без объяснения в комментарии
- **Только `interface` для объектов**, `type` для unions/utility-типов
- **Все async функции** возвращают `Promise<T>` явно

### Имена

- Файлы: `PascalCase.tsx` для компонентов, `camelCase.ts` для утилит
- Компоненты: `PascalCase`
- Хуки: `useCamelCase`
- Константы: `UPPER_SNAKE_CASE`
- Переменные и функции: `camelCase`
- **Имена на английском**, даже в проекте на русском
- Текст для пользователя — через i18n, не хардкодить русские строки в JSX

### Структура файла React-компонента

```tsx
// 1. Импорты — сначала external, потом internal
import { useState } from 'react'
import { View, Text } from 'react-native'

import { Button } from '@/src/components/ui/Button'
import { useFamily } from '@/src/features/family/hooks'

// 2. Типы и интерфейсы
interface Props {
  taskId: string
}

// 3. Компонент
export function TaskCard({ taskId }: Props) {
  // hooks вначале
  const family = useFamily()
  const [isOpen, setIsOpen] = useState(false)
  
  // обработчики
  const handlePress = () => setIsOpen(true)
  
  // рендер
  return <View>...</View>
}
```

### Комментарии

- **Не пиши комментарии для очевидного.** Хорошие имена заменяют комментарии.
- **Пиши «Why», не «What».** Не «увеличиваем счётчик», а «после третьей попытки выходим — это спасает от бесконечного цикла при сетевых ошибках».
- Комментарии на русском **разрешены**, если объясняют сложную бизнес-логику.

## 5. Безопасность (КРИТИЧНО)

### Ключи и секреты

- **Никогда** не зашивай API-ключи (OpenAI, Anthropic, Supabase service_role) в код приложения
- Все секреты — в `.env` для локалки и `supabase secrets` для продакшена
- В Git коммитят только `.env.example` с пустыми placeholder'ами
- В Edge Function ключи доступны через `Deno.env.get('KEY_NAME')`
- В мобильном приложении — только публичные ключи (Supabase anon key)

### Row Level Security

- **Каждая** таблица в Postgres должна иметь RLS-политики
- Политики добавляются в **той же миграции**, что и сама таблица — не в отдельной
- Базовое правило: юзер видит только данные семей, в которых состоит
- При создании новой таблицы напиши тесты на RLS (даже если автотесты не используются — хотя бы вручную проверь, что чужие данные не видны)

### Edge Functions

- AI-сервисы (Whisper, Claude) вызываются **только** из Edge Functions
- На клиенте — только публичные API без чувствительных ключей
- Edge Function проверяет авторизацию пользователя перед обработкой

## 6. Работа с Supabase

### Миграции

- Создавать через `supabase migration new <name>`
- Имя файла: `<timestamp>_<snake_case_name>.sql`
- Внутри: каждая команда заканчивается `;`
- Включать в одну миграцию: создание таблицы + индексы + RLS-политики
- **Никогда** не редактировать уже применённую миграцию — создавать новую

### Edge Functions

- Структура папки `supabase/functions/<name>/`:
  ```
  index.ts          # точка входа serve()
  helpers.ts        # вспомогательные функции (если есть)
  prompts.ts        # промпты для AI (если есть)
  ```
- Использовать `_shared/cors.ts` для CORS-заголовков
- Все ошибки возвращать как JSON с понятным message

### Realtime подписки

- Подписки **обязательно** отписывать при unmount компонента
- Использовать `useEffect` с cleanup-функцией
- Не подписываться более одного раза на тот же канал

## 7. Стиль коммитов и PR

### Conventional Commits

Каждый коммит:
```
<type>(<scope>): <subject>
```

Типы:
- `feat:` — новая фича
- `fix:` — исправление бага
- `chore:` — рутинная работа (зависимости, конфиги)
- `refactor:` — переработка без изменения поведения
- `docs:` — изменения в документации
- `test:` — добавление или правка тестов
- `style:` — форматирование, без изменения логики

Scope — обычно номер тикета Jira:
```
feat(HT-12): добавить sign-up экран
fix(HT-7): исправить race condition в очереди оффлайн-мутаций
```

### Один коммит — одна логическая единица

Не делать «гигантские коммиты» с десятком разных изменений. Один логический шаг — один коммит.

### Pull Requests

- Имя ветки: `feature/HT-XX-краткое-описание`
- Имя PR: точно как Summary тикета Jira
- В описании обязательно `Closes HT-XX` для авто-закрытия тикета при мерже

## 9. Что НЕ делать в продукте (общие ограничения)

❌ **Не использовать swipe-actions** на задачах в списке (продуктовое решение).

❌ **Не предлагать категории, теги, приоритеты, recurring задачи, календарь** — явно out of scope.

❌ **Не использовать realtime для всего подряд** — только там, где нужно (комментарии). Для задач — pull-to-refresh + при возвращении в foreground.

❌ **Не использовать `console.log`** в финальном коде. Только в процессе отладки, удалять перед PR.

❌ **Не зашивать тестовые данные** в продакшен-код. Mock-данные — только в тестах.

❌ **Не игнорировать ошибки TypeScript** через `any` или `@ts-ignore`. Решай причину.

❌ **Не запускать `git push --force` в master.**

❌ **Не пропускать pre-commit hooks через `--no-verify`.** Если что-то не проходит — чини причину.
